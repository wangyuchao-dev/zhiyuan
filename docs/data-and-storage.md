# 数据与存储：四个「要不要」的判断

> 这份文档回答四个常被问、也常被答错的问题：要不要加 Redis、要不要换 Milvus、
> 要不要做后置覆盖、要不要单独做清洗。每个都给出**判据**和**本项目的结论**，
> 结论后面跟着代码位置 —— 能核对的结论才算结论。

## 一、要不要加 Redis

**判据**：有没有「同一个输入被反复算」的环节，且这个环节足够贵（>100ms）。

| 情况 | 结论 |
|---|---|
| 单机 demo、一次问答只跑一次 | 不加。加了只是多一跳网络 |
| 检索 + embedding 是主要耗时（本项目 4.18s） | **必须加**，这是纯函数，重复算就是浪费钱 |
| 有多个实例 | 必须加（本地缓存不跨进程） |
| 要限流 / 在途去重 / 任务进度 | 必须加，这些本来就需要共享状态 |

**本项目结论：加。** 实测检索 4.18s → 0.32s、生成 14.1s → 0.03s。

实现见 `core/cache.py`，三条约束值得单独说：

1. **key 里带语料指纹** —— `corpus_fingerprint(文件哈希列表)`。加一份文档、删一份文档，指纹变，旧缓存自动失效。不靠人记得清缓存（**这是被「加城市忘清缓存」坑过之后改的**）。
2. **空结果与异常不缓存** —— 一次 embedding 抖动不能污染接下来 30 分钟。
3. **连不上就降级** —— `build_cache()` 连不上 Redis 时自动退化成进程内缓存，接口行为不变，服务照常起。

```python
cache = build_cache(settings.redis_url)         # 连不上自动降级，不会起不来
key = cache.build_key("retr", question, corpus_fp=fp,
                      params={"k": 5, "min_score": 0.3})
items, hit = cache.get_or_set(key, lambda: retriever.search(question))
```

## 二、要不要换成 Milvus

**先说结论：不换。** 不是因为 Milvus 不好，而是因为**不该为想象中的规模选型**。

行业上比较一致的决策树（腾讯云开发者社区、Milvus 官方对比文档口径一致）：

| 现状 | 建议 |
|---|---|
| 已有 PG，向量 < 500 万 | pgvector（向量与业务同库，能写 JOIN，运维零新增） |
| 已有 ES，且需要混合检索 | ES 的 kNN + BM25（BM25 是老本行） |
| 千万级、自建、要高 QPS | Qdrant（简单）或 Milvus（全功能） |
| 亿级 / 不想运维 | 云托管 |

Milvus 官方对比表里，Milvus 的强项写得很清楚：**多租户靠 partition key、高选择率多列过滤、服务端 BM25 混合检索、亿级水平扩展** —— 这四条本项目一条都不占：

- 向量总量：4 份文档 → 42 个 chunk（真实语料），连 pgvector 都嫌重
- QPS：个位数
- 过滤：按文档 hash 过滤，一个等值条件
- 运维：单机

**什么时候该换**（写在这里，等真撞上再动手）：

1. chunk 数 > 100 万，且 HNSW 索引放不进内存；
2. 需要服务端 hybrid（向量 + BM25 一次调用）而不是两路自己融合；
3. 需要多租户隔离（partition key）与副本高可用；
4. P99 检索延迟超过 200ms 且加内存无改善。

迁移成本其实很低：**向量是 append-only 的，导出重建索引即可**，不用做数据迁移脚本。所以现在把重排/召回封装在 `querying/parallel.py` 的接口后面，换库只改一个适配器。

> 一句话：**先确认 chunk 质量与 hybrid 检索，再考虑换库。** 换库解决不了「切分和召回策略不对」的问题。

## 三、要不要做后置覆盖

**先分清两件事**，它们的名字很像，做法完全不同：

| | 后置覆写（overwrite） | 后置校验（postcheck） |
|---|---|---|
| 适用 | 输出是**结构化字段**（日期、序号、预算合计） | 输出是**自然语言** |
| 做法 | 程序按事实**重算并覆盖**模型产出的值 | 程序**核对**模型说的值在证据里有没有，没有就拦 |
| 例子 | 知旅：行程日期、第几天、预算合计由程序重算 | 知渊：错误码、带单位数字、日期必须在证据里 |
| 理由 | 这些字段有唯一正确答案，让模型算就是引入噪声 | 答案不能重算，只能判断「有没有编」 |

**本项目结论：做校验，不做覆写。** 因为答案是自然语言，没有「正确答案」可以重算。
但如果**用程序把 15 分钟改回 5 分钟**，那是在替模型编第二个答案 —— 正确做法是拦掉、重答或降级。

实现见 `core/postcheck.py`，四类确定性错误 + 三种处置：

| 检查 | 抓什么 | 处置 |
|---|---|---|
| `check_codes` | `E1035` 这种类错误码不在证据里 | **BLOCK**，换保守话术 |
| `check_unit_numbers` | 「500 MB」「15 分钟」与证据不符 | **BLOCK** |
| `check_dates` | 日期漂移（11-20 → 12-20） | **BLOCK** |
| `check_citations` | 引用 `[7]` 但只有 3 条证据 | **ANNOTATE**，移除越界编号 |

只查「强特征」（类错误码、带单位的数字、日期），不查裸数字 —— 裸数字误报太多（页码、条目序号都像）。

```python
report = postcheck(answer, evidence)
if report.action is Severity.BLOCK:
    answer = report.answer          # 保守话术
```

## 四、要不要单独做清洗

**要，而且必须在切分之前。** 理由很实际：页眉页脚是**跨页重复**的，
只有拿到整篇文字才识别得出来；切分之后再处理，已经晚了。

五类必清（`indexing/clean.py`）：

| 类型 | 为什么必须清 |
|---|---|
| 页眉页脚 | 每页重复，进索引后「公司名」变高频词，检索被污染 |
| 页码 / 「第 x 页 共 y 页」 | 纯噪声，还会让「3」变成关键词 |
| 目录行（`第一章 ...... 12`） | 切分后是半句话，向量上容易命中但没价值 |
| 全角数字字母（`５０ＭＢ`） | 检索 `50MB` 永远找不到 |
| 连续重复段 | 扫描件双栏重叠、复制粘贴残留 |

还有一道**质量门槛** `quality_gate()`：清洗后少于 50 字、或保留率低于 30%，直接拒收并提示「疑似扫描件/加密文档」。
**宁可拒收，也不要把半页乱码灌进向量库** —— 脏数据进库之后，所有评测都是白跑。

## 五、大文本到底测没测

测了，在 `tests/test_data_pipeline.py` 的 `TestLargeDocument`：

```
生成 800 页模拟手册（页眉 + 页码 + 全角字符 + 重复段 + 错误码）
  → 原文 680,887 字
  → 清洗 85ms，去掉 800 行页眉、800 行页码，保留 663,394 字（97.4%）
  → 父子分块 204ms，得到 800 个父块 / 3,200 个子块
  → 上下文预算 1500 token：100 条证据只装得下 7 条，其余丢弃且在 stats 里可见
```

断言里除了数值，还有两条是「不丢内容」：

- `test_children_cover_whole_document`：子块拼起来必须覆盖 90% 以上正文（防切分漏块）；
- `test_context_budget_holds_under_load`：预算必须真的生效，且 `evidence_dropped` 要能说清丢了多少。

> 为什么用合成文档：真实 PDF 有版权也不能进仓库。合成文档保留了**结构特征**（页眉/页码/重复/全角），
> 能验证「清洗规则是否生效」「分块是否漏内容」，不验证语义质量 —— 语义质量归 `eval/`。

## 六、这一层的边界

- Chroma 是单机持久化目录，多实例共享要换服务端；真到那天按第二节的判据再选
- 清洗规则是按「平台类文档」写的，换成合同/法规后要重调（尤其页眉识别）
- 后置校验只抓确定性错误，抓不住「语义上答偏了」—— 那要靠 `eval/` 的 grounding 指标 + 人工抽检
- Redis 缓存的是检索结果，**不缓存生成结果**：生成有随机性，缓存会让人误以为模型很稳定
