# Agent 设计：十个绕不开的选型问题

> 每个问题给三样东西：**结论 → 判据 → 在知渊里怎么落**。
> 这份文档随项目改，不写「教科书答案」，只写本项目实际的选择和理由。

## 1. ReAct 还是 Plan-and-Execute

**结论**：能枚举步骤就用 Plan，必须边走边看才用 ReAct；生产上通常是「外层 Plan + 内层局部 ReAct」。

**判据**：计划能不能在动手前写死？执行中会不会「看到结果才知道下一步」？

**在知渊里**：`_quick_intent` 先快判意图（规则命中直接定路由），判不了才让模型分类 —— 这是**外层的确定性计划**；
`RAG` 分支内部（检索 → 精排 → 生成）是固定流程，不需要 ReAct。真正有 ReAct 味道的只有「查询改写」：无指代词时跳过，有指代才调模型。

**代价**：灵活性不如纯 ReAct（遇到没预设的意图会落到默认分支），换来的是**成本和可预测性**。

**代码**：`agent/plan.py` —— `build_plan()` 用规则决定链路（闲聊不检索），`execute()` 只在单步内做**有界重试**，每次尝试都进 trace。

## 2. Agent 还是 Workflow

**结论**：主干确定就是 Workflow，只在结尾留一个 Agent 兜底；**不要为了让项目显得"智能"把主干交给模型**。

**判据**：这条链路的步骤和顺序是否每天都一样？如果一样，用代码编排比用模型规划更便宜、更可控、更好测。

**在知渊里**：整条链路是代码编排的 workflow（意图 → 检索 → 精排 → 生成），只有「生成答案」这一步是真 Agent（模型自由组织语言）。
连「要不要改写查询」都是规则判断，不是模型决定。

**代码**：`agent/plan.py` 的 `Step.kind` 区分 `workflow` 与 `agent`：主干四步全是 workflow，只有 `compose` 是 agent。

## 3. 工具调用失败怎么办

**结论**：先给错误分类，再定策略；错误信息要**翻译成模型能看懂的人话**，让它自己改参数。

| 错误类型 | 例子 | 策略 |
|---|---|---|
| 瞬时错误 | 超时、限流、5xx | 退避重试 2~3 次，不重做上游 |
| 参数错误 | 城市名不存在、日期格式错 | 把「哪错了 + 合法值」返回给模型，让它改 |
| 权限错误 | 越权查别的部门 | **不重试**，直接拒（重试只会放大越权尝试） |
| 逻辑错误 | 检索为空 | 降级：放宽阈值只取 top-1，或回答「材料里没有」 |

**在知渊里**：检索为空时不是抛异常，而是走「材料中没有」的兜底话术；API 层 `deps.py` 懒加载，模型没配 Key 也能起服务并返回健康检查结果。

**代码**：`core/errors.py` —— 五类错误（transient/param/permission/empty/logic）+ `next_delay()` 退避序列 + `to_model_message()` 翻译；`tools/registry.py` 做参数与权限校验。

## 4. 多 Agent 怎么协作

**结论**：能用单 Agent 就别多 Agent。多 Agent 只在**三个条件同时成立**时才值得：任务可明显并行、子任务上下文互不干扰、合并成本低于收益。

**为什么克制**：每多一个 Agent 就多一层上下文传递、多一份 prompt 维护、多一组失败组合。常见的「主控 + worker」最后都退化成「主控被 worker 的错误答案带偏」。

**在知渊里**：单 Agent（一个 `Agent` 类）+ 三个独立模块（意图 / 记忆 / 检索）。
**没有**拆成「检索 Agent + 回答 Agent」——因为检索是确定性的函数调用，拆成 Agent 只会让延迟翻倍。

**代码**：**没有新增代码** —— 这就是结论。`agent/plan.py` 的 `Plan` 可打印，一条链路一眼看全，不为「看起来高级」拆 Agent。

## 5. MCP 和 Function Calling 是什么关系

**结论**：Function Calling 是**模型侧的能力**（模型把"我要调什么、参数是啥"说出来）；MCP 是**连接侧的协议**（工具在哪、怎么连、怎么描述）。**两者最终都要落到 function calling 上**。

```
模型 → 产出 tool_call（JSON） → 执行方（你的代码 / MCP client） → 结果回填 → 模型继续
```

- 函数在哪执行：在你的进程里（本地工具）或 MCP server 里（远程）
- 怎么连数据库：不直连。业务接口封装成工具，权限在接口层判
- 不同模型格式怎么对齐：LangChain / LangChain4j 这类框架做适配层，把各家 tool_call 格式统一

**在知渊里**：没有走 MCP，直接本地函数调用 —— 因为工具只有检索和文档管理，都是进程内调用，加一层 MCP 只是多一跳。
（知识库场景真正需要 MCP 的是「接外部系统」，比如 OA、工单、法务系统。）

**代码**：`tools/registry.py` 生成 function calling 描述；`tools/mcp_adapter.py` 做 MCP ↔ 本地互转，并按前缀筛选、限制数量（工具描述也占上下文）。

## 6. 记忆怎么做

**结论**：先分类型，再谈存储。**事实、偏好、临时状态必须分开**，否则检索时噪音会淹没真信号。

| 类型 | 生命周期 | 存法 | 检索策略 |
|---|---|---|---|
| 短期（当前窗口） | 几轮，随对话淘汰 | 内存 + 消息列表 | 全量带进 prompt，容量有限 |
| 事实（部门、岗位） | 长期，几乎不变 | 结构化存储 + 版本号 | 命中即取，不过相似度 |
| 摘要（更早对话） | 长期，会更新 | 单独一张表 | 只在长对话时带一段 |
| 临时状态（"刚才那个文档"） | 分钟级 | 会话上下文 | **不进长期库** |

**在知渊里**：`memory.py` 就是这三层的协调者 —— `chat_history_manager`（窗口原文）、`facts_manager`（稳定事实）、`summary_manager`（压缩摘要），落 SQLite。

**踩过的坑**：一开始把所有中间状态都写进长期记忆，检索时全是垃圾。后来定死「临时状态只在会话内」，并给事实加了版本号（同 key 覆盖，不追加）。

**代码**：`agent/memory_policy.py` —— 四类（fact/preference/ephemeral/summary）、版本号、写入门槛（疑问句/寒暄/超长不写）、检索至少 2 个共同词且只放 1 条。

## 7. 召回率低怎么办

**结论**：稀疏 + 稠密双路召回 → 并行 → 父子分块 → rerank。**顺序不能反**：先保证召得回，再谈排得准。

**在知渊里**：向量（稠密）+ BM25（稀疏，bi-gram 切词）→ RRF 融合（0.7 / 0.3）→ qwen3-rerank 精排 → 阈值 0.3 过滤。
实测 34 题：纯向量 82.4% → 混合 91.2%，**编号密集型 5/8 → 8/8**（纯向量对 `E1017` 这类符号几乎无效）。

**没做的**：父子分块（当前语料 chunk 只有 42 个，父子分块的收益抵不上实现成本；文档量上 10 倍再做）。

**代码**：`indexing/parent_child.py`（child 检索 + 回溯 parent，按 parent 去重）+ `querying/parallel.py`（并行 + 单路超时 + RRF 融合，单路挂了自动降级）。

> 注：`parent_child` 已实现并有测试，但**未接入主链路**。对照实测显示，当前 1300–4400 字的语料下单轮问答用 200 字 child 与用 980 字 parent 的答案完全一致，而 parent 更吃上下文预算，所以按现状不接。判断依据写在 `parent_child.py` 文件头。

## 8. MCP 与 SKILL 的区别

**结论**：MCP 解决「**能不能碰到**外部系统」，SKILL 解决「碰到之后**怎么干**」。两者是合作关系，不是替代。

| | MCP | SKILL |
|---|---|---|
| 本质 | 协议：标准的工具/资源描述与调用 | 模块化能力包：一份写给模型看的操作手册 |
| 加载 | 连上就能用（工具列表） | **只加载名字与简介**，命中才展开全文（懒加载） |
| 解决 | 连接与鉴权 | 流程与最佳实践 |

**为什么 SKILL 要懒加载**：几十个技能的全文塞进提示词会直接挤爆上下文，而且稀释注意力。只放 `name + description`，模型判断相关了再取正文 —— 这就是「渐进式披露」。

**在知渊里**：目前两者都没用（单 Agent + 进程内工具）。如果要做「合同审查」这类有固定流程的能力，会做成 SKILL；要接外部法务系统，会用 MCP。

**代码**：`skills/registry.py` —— 只读 front-matter 建目录，`render()` 命中才 `load_body()`；示例技能 `skills/fault-code-lookup/SKILL.md`。

## 9. Agent 效果怎么评估

**结论**：任务成功率（TSR）+ 错误修复率，离线评测防回归，线上控延迟与错误率。**mock 锁死链路**保证指标本身没坏。

**在知渊里**：`eval/` 七维框架，39 条用例（静态 20 / 动态 8 / 安全 6 / 故障 5）。
`--runs 5` 看 `pass@5` 与 `pass^5` 的差距；两次结果按 `case_id` 对齐可算错误修复率。

**口径**：TSR 只取首次运行；稳定性单独报；**绝不把「至少过一次」当 TSR**。

**代码**：`eval/`（七维）+ `eval/compare.py`（错误修复率与回归，按 `case_id` 对齐，分母为 0 时返回 None 而不是 0）。

## 10. 上下文太长怎么办

**结论**：分级处理 —— 先局部裁剪，再设单条预算，最后才考虑摘要。

| 手段 | 做法 | 代价 |
|---|---|---|
| 局部裁剪 | 只带最近 N 轮 + 命中的记忆 | 可能丢远距离指代 |
| 单条预算 | 单个证据片段截断到 N 字，工具返回超长就摘要 | 细节丢失 |
| 摘要压缩 | 老对话压成一段 | 一次额外调用，且不可逆 |

**在知渊里**：`history_limit` 控制带几轮原文；检索只取 top-3 且过阈值；超长文档在切分时就限制了 chunk 大小（切太碎丢上下文，切太大检索不准）。

**原则**：**先减少「带什么」，再考虑「压多短」** —— 大部分上下文爆炸是"什么都往里塞"造成的，不是摘要做得不够好。

**代码**：`core/context_budget.py` —— 事实必带、证据按分数并逐条截断、历史整轮从新到旧；丢弃与截断的数量都写进 `stats`，裁了多少必须可见。
